# FIFUZZ 与 EH-Fuzz：方法、实验与对 ext4 一致性测试的启示

分析日期：2026-11-16。

本文依据本目录的两份 PDF，核对正文、主要实验表和消融实验；结合仓库的 README、counter-trace 反馈说明与 source-fault-study 说明讨论应用方向。论文实验数据均为作者报告，本次没有运行两套工具、重现论文实验或验证仓库历史 bug。下文明确区分论文结论、分析判断和后续建议。

EH-Fuzz 明确基于 FIFUZZ 实现。理解这条研究路线，可以沿着三个问题展开：

1. **如何触发错误处理？** 主动模拟内存分配等操作的失败。
2. **让哪一次上下文中的操作失败？** 用调用上下文区分同一源码位置。
3. **如何决定继续探索什么？** 从普通代码覆盖，发展为上下文相关的错误覆盖。

进一步用于文件系统测试时，还需解决第四个问题：**错误处理完成后，内存与磁盘状态是否符合语义约束？** 这正是两篇方法与当前仓库的一致性 oracle 可以结合的地方。

## 2. 共同研究问题：常规输入变异遗漏了什么

论文区分两类错误：

| 错误类型 | 例子 | 主要触发条件 |
| --- | --- | --- |
| 输入相关错误 | 文件格式损坏、非法参数、长度越界 | 修改程序输入 |
| 偶发环境或资源错误 | 内存分配失败、网络连接失败 | 环境、资源或底层操作失败 |

即使输入变异已经覆盖大量正常分支，也未必能使某个深层 `malloc()` 恰好返回 `NULL`。错误处理还经常涉及跨函数传播、部分初始化和资源回收，因此“很少执行”与“容易写错”同时存在。

FIFUZZ 的前期人工研究在 9 个应用的 824 个文件中统计到 6,168 个错误位置，其中 2,616 个，即约 42%，与偶发错误有关。它还研究了 393 个已有 fuzzer 发现的 CVE：121 个与错误处理有关，其中 11 个与偶发错误有关。这里的约 9% 是 **11/121**，不是 11/393。（FIFUZZ §2.3–2.4，表 1–2，PDF 第 4–5 页。）

这些数字支持研究动机，但属于特定样本，不能推广为所有软件的固定比例。输入与环境也并非绝对独立，例如输入能影响内存压力；论文要解决的是普通输入变异难以稳定、精确地控制特定资源失败。

## 3. 第一篇：FIFUZZ

### 3.1 核心创新：上下文敏感的错误点

传统按源码位置注入的做法，可能在程序第一次经过公共辅助函数时就失败、提前退出，导致后续重要错误路径一直无法到达。

论文图 1 的例子可概括为：

```text
main → FuncA → FuncP → malloc
main → FuncB → FuncP → malloc
```

两个调用最终到达同一个 `malloc` 源码位置。`FuncB` 在调用 `FuncP` 前已经释放参数，而 `FuncP` 的分配失败分支又会释放该参数。要观察到 double free，需要让 `FuncA` 路径中的分配正常执行，并在 `FuncB` 的上下文中触发分配失败。

FIFUZZ 将错误点定义为：

```text
ErrPt    = <ErrLoc, CallCtx>
CallCtx  = [CallInfo1, CallInfo2, ..., CallInfoN]
CallInfo = <CallLoc, FuncLoc>
```

其中 `CallLoc` 是调用位置，`FuncLoc` 是被调函数位置。因此，即使函数名序列相同，只要某一层调用位置不同，也可以区分为不同上下文。论文的 bison 案例说明了这种区分的价值。（§3.2；§5.3 图 11。）

**分析判断：贡献在于给故障输入增加上下文维度，使深层错误路径可以被单独探索。**

### 3.2 错误序列与搜索过程

论文用由错误点及其 0/1 值构成的 `ErrSeq` 表示故障选择：

- `0`：正常执行该调用，不强行注入失败；这不保证真实调用一定成功。
- `1`：向该错误点注入失败。

其表示可通过 `Hash(ErrPt) → 0/1` 的哈希表实现。搜索流程为：

1. 先正常运行输入，收集能够到达的错误点，构造初始全零序列。
2. 初始变异逐个将错误点从 0 改为 1，探索单错误点失败。
3. 按序列重新运行，动态匹配位置和调用上下文；被匹配的错误点才注入。
4. 失败可能改变后续控制流，使部分原错误点不可达，并暴露新的错误点。
5. 如果本轮增加代码覆盖，对原序列及新收集序列进行单点翻转、去重，继续搜索。
6. 如果没有增加代码覆盖，放弃由这次执行继续变异的机会。

这里同时存在普通输入变异。后续 EH-Fuzz 对 FIFUZZ 的描述明确指出，两类变异共用代码覆盖，并随机选择输入变异或错误变异。（FIFUZZ §3.3、§4.2；EH-Fuzz §II-C、§IV-C。）

**关键局限：注入操作考虑了上下文，判断种子是否有价值的反馈仍主要是普通代码覆盖。** 新输入可能到达一个新的错误调用上下文，却没有覆盖新分支；这种输入仍可能被丢弃。

### 3.3 如何找到注入位置

FIFUZZ 在 LLVM IR 上分析及插桩，候选错误位置主要是函数调用：

1. 返回指针或整数，并在 `if` 中与 `NULL` 或零比较。
2. 优先选择外部库函数调用，避免在包装函数与底层函数重复注入。
3. 按函数统计返回值被检查的比例，超过阈值 `R` 后，将该函数的调用提取为候选；实验取 `R = 0.6`。
4. 人工选择真正可能失败、确实表示错误的函数及调用。

实际注入会跳过目标调用，代入 `NULL` 或负整数返回值。函数调用、进入和退出处的插桩维护运行时调用上下文。（§4.1，PDF 第 7–8 页。）

9 个应用中提取了 9,795 个候选调用，人工确认 1,822 个真实错误位置，候选精确率为 18.6%。因此，它提供的是辅助提取能力，实验仍依赖人工确认；不能把候选误判率当作最终 bug 报告误报率。（表 4。）

### 3.4 实验结果与可支持的结论

| 指标 | FIFUZZ 报告 |
| --- | --- |
| 主要评测对象 | 9 个用户态 C 应用 |
| 运行方式 | 带 ASan 与不带 ASan 两种配置，每个应用各运行 3 次，每次限时 24 小时 |
| 去重告警 | 317 |
| 按根因去重的 bug | 50 |

| 开发者已确认 | 32 |

同一错误位置可在不同上下文暴露不同 bug，说明仅按静态注入位置去重会丢失信息。另一方面，317 个告警经过根因分析只对应 50 个 bug，说明崩溃位置或注入上下文也不能直接当作独立根因。

论文还做了两个比较：

- **上下文消融：** 表 8 报告上下文不敏感版本找到 9 个 bug，完整 FIFUZZ 为 50 个。该实验支持上下文区分的价值；严格复现时仍需核清表 8 中 bug 数与前文 ASan/非 ASan 合并统计的关系。
- **独立 Binutils 实验：** 在旧版 Binutils 2.26 的 5 个工具上，FIFUZZ 找到 14 个 bug，其中 12 个错误处理 bug 未被四个基线找到。但 AFLSmart 和 FairFuzz 也各找到一个 FIFUZZ 漏掉的输入相关 bug。故 FIFUZZ 并非在所有程序和所有 bug 上全面覆盖其他工具。（§5.5–5.6，表 8–9。）

## 4. 第二篇：EH-Fuzz

### 4.1 从“在哪里注入”推进到“用什么反馈搜索”

EH-Fuzz 保留 FIFUZZ 的上下文敏感错误点，并将实际执行到的错误点及成功/失败状态组成的错误序列作为反馈。

用分析性的记号表示：

```text
C_code = 已覆盖的代码分支集合
C_err  = 已实际覆盖的上下文相关错误序列集合
```

两个测试可以有相同的 `C_code`，但包含不同的错误上下文或不同的成功/失败组合。EH-Fuzz 将这类差异视为潜在的新搜索机会。

**“错误覆盖”不等于错误处理分支数量，也不等于注入次数或 bug 数。** 论文实际用已覆盖的不同错误序列来度量它，没有给出“所有可能错误序列”的分母，因此不宜直接称为完整状态空间的覆盖百分比。（§III-A–C，PDF 第 4–5 页。）

### 4.2 区分计划注入与实际执行

EH-Fuzz 明确维护两类序列：

| 序列 | 含义 | 用途 |
| --- | --- | --- |
| possible error sequence | 根据此前执行推导的候选故障方案 | 指导注入 |
| covered error sequence | 本次真实运行到的错误点及状态 | 计算错误覆盖 |

例如，计划在 A 和 B 两点失败，但 A 失败使程序提前返回，B 根本没有执行。此时不能把“B 失败”算入实际覆盖。

当实际错误序列是新的，工具保留对应的计划与实际序列，分别进行单点翻转和去重。该设计避免把计划执行当成已完成执行，也保留了故障改变可达路径后产生的新信息。（§III-C。）

### 4.3 将输入变异与错误变异分开反馈和调度

EH-Fuzz 采用两套反馈与种子池：

| 搜索对象 | 主要反馈 |
| --- | --- |
| 输入变异 | error-unrelated code coverage |
| 故障序列变异 | error coverage |

`error-unrelated code coverage` 的实现定义较具体：先找出包含已识别错误位置的基本块，将经过这些块的分支认作错误相关分支，再对其余分支采集覆盖。（§IV-A。）

调度采用贪心切换：先进行错误变异；连续提供 `N` 个错误序列仍无错误覆盖增长，切换到输入变异；连续提供 `N` 个输入仍无对应代码覆盖增长，再切回错误变异。实验中，作者将 `N` 设为已执行测试数的 10%，并比较了 10%–50% 的取值。（§III-D，§V-F。）

**分析判断：两类反馈提供了更有针对性的搜索信号，但这个静态分支划分不构成严格的因果分离。** 故障同样可能改变不包含注入点的下游分支，输入也会影响错误点的可达性。论文自己承认两种变异会互相帮助。

### 4.4 工程扩展

EH-Fuzz 增加了返回值的 Andersen-style 别名分析，减少遗漏间接检查；用户态输入生成参考 AFL++，内核模块输入生成参考 Syzkaller。

为了支持内核，它还处理两类问题：

- 通过独立信息收集线程和消息传递降低目标线程的监控负担。
- 用 `in_interrupt()` 区分中断处理上下文，避免把中断函数错误地记作被中断函数的普通被调用者。

错误位置提取仍需要人工选择：5,370 个候选中确认了 3,001 个真实位置，候选中约 44.1% 未被认可。论文将其与 FIFUZZ 的约 81% 比较；两个总表来自不同版本及目标集合，该跨论文比例不宜单独作为别名分析因果收益的严格证明。（§IV、§V-B。）

| --- | --- |
| 评测范围 | 9 个用户态应用、6 个 Linux 5.16.16 内核模块 |
| 文件系统 | btrfs、xfs、jfs、cephfs |
| 驱动 | xhci、vmxnet3 |
| 运行方式 | 用户态 ASan、内核 KASan；每个目标运行 3 次，每次限时 24 小时 |

| 错误处理 / 输入相关 bug | 39 / 6 |

| 单错误点失败触发的错误处理 bug | 37/39 |

来源：表 II、表 IV，§V-C，PDF 第 8–10 页。

**论文没有评测 ext4。** 它证明了方法可用于若干内核文件系统和驱动，但不能由此推定已经验证 ext4 的故障恢复与持久化一致性。

在本篇论文同一组对照实验中：

- 用户态基线 AFL、AFL++、FIFUZZ 合计发现 18 个不同 bug，EH-Fuzz 覆盖这些 bug，并额外发现 13 个。
- 内核基线 Syzkaller、FIZZER 合计发现 7 个不同 bug，EH-Fuzz 覆盖这些 bug，并额外发现 7 个。
- 合计比所比较基线的发现并集多 20 个 bug。

这比直接比较“第一篇 50、第二篇 45”有意义。两篇主实验的时间、版本和评测范围不同，50 与 45 不能直接比较工具强弱。（§V-E，表 VI。）

### 4.6 消融实验：最值得读的一张表

EH-Fuzz 表 VII 在 9 个用户态应用上比较以下配置：

| 配置 | 分支覆盖总数 | 已覆盖错误序列 | bug 数 |
| --- | ---: | ---: | ---: |
| FIFUZZ | 160,198 | 4,565 | 15 |
| FIFUZZ + 别名分析 | 257,061 | 179,312 | 22 |
| 再加错误覆盖反馈，随机调度 | 251,425 | 732,871 | 24 |
| 别名分析 + 自适应调度，仍用代码覆盖 | 259,305 | 177,500 | 19 |
| 完整 EH-Fuzz | 225,968 | 1,036,117 | 31 |

来源：表 VII，PDF 第 13 页，印刷页 1736；数字已对照 PDF 页面图核对。

可以得出三个有边界的结论：

1. **完整方案发现的 bug 最多，但普通分支覆盖不是最高。** 这说明分支总数不足以解释错误处理 bug 的发现能力。
2. 错误覆盖反馈使上下文相关的错误探索显著增加，完整组合获得更好的 bug 结果。
3. 单加自适应调度的变体为 19 个 bug，低于仅增加别名分析的 22 个。因此，不能把每个组件都描述成独立、单调提升性能；表中体现的是组合效果，机制之间存在交互。

表格没有充分展示各指标的多次运行分布、置信区间及显著性，且部分变体实现条件不同。因此适合说“这组实验支持完整方案的效果”，不宜宣称普适最优或已严格分离各项因果贡献。

### 4.7 一处需要核对的数据表述

§V-C 正文说，生成的错误序列约 4% 有效，生成的程序输入只有 0.01% 有效。表 IV 的总数为：

```text
错误序列：190,334 / 4,767,052 ≈ 3.993%
程序输入： 21,024 / 17,986,395 ≈ 0.1169%
```

按表中总数相除，后者约为 **0.117%**，与正文的 0.01% 不一致，可能是笔误或未解释的统计口径差异。汇报时应标明这一点，避免据正文直接推导夸大的效率倍数。

即使比例一致，两者的“有效”也依据不同反馈判定，执行代价和测试分布不同；有效样本比例不能直接当作单位时间发现 bug 的效率。

## 5. 对两篇工作的总体评价

### 5.1 最有价值的研究启示

**第一，故障本身可以成为被变异的输入。** 测试空间可从程序输入 `x` 扩展到 `(x, 故障方案)`，使原本依赖偶发环境的路径成为可控搜索对象。

**第二，反馈应保留与目标缺陷有关的信息。** 若目标 bug 依赖调用上下文，仅以分支集合判定种子价值，会合并掉重要差异。EH-Fuzz 将注入时使用的上下文信息也纳入了搜索反馈。

**第三，先单错误点、后组合探索有实证依据。** FIFUZZ 的 42/46、EH-Fuzz 的 37/39 错误处理 bug 都只需一个错误点失败。这个结果支持优先探索有意义的单点失败，但仅适用于这两组内存错误占主导的样本，不能直接推广为所有文件系统恢复 bug。

另需区分：**一个错误点失败不一定等于一次动态调用失败。** 论文的错误点身份由位置和调用栈构成，未显式纳入同一上下文的第几次执行。尤其 FIFUZZ 的哈希表示，不能直接理解为逐次调用的完整时间轨迹。

### 5.2 共同限制与进一步研究空间

| 限制 | 对文件系统测试的影响 |
| --- | --- |
| 主要对特定调用返回值注入错误 | 不直接覆盖坏 DMA 数据、部分写、持久化顺序等其他故障模型 |
| 注入时跳过调用，代入失败返回值 | 必须核对被调函数真实失败时的部分副作用、清理、事务状态和错误码语义 |
| 调用栈是主要上下文 | 相同调用栈下，事务阶段、对象生命周期、磁盘初态可能不同 |
| 错误序列使用二值成功/失败 | 不同 errno 的恢复语义未在该二值模型中充分区分 |
| 完整错误组合可能快速增长 | 对固定 n 个二值点，候选状态最坏可达 2^n；更多序列未必有更多语义价值 |
| 检测依赖崩溃及 ASan/KASan 等 | 无崩溃的磁盘计数失配、目录引用不一致可能没有自动报警 |
| 输入、配置和可达性仍有限 | 错误点存在并不意味着当前工作负载能执行到它 |
| 实验与人工确认共同支撑结果 | 不能据“实验中无误报”推导任意目标、任意故障组合都无误报 |

特别需要谨慎理解 EH-Fuzz §VI-A 对“不可能序列不会造成误报”的说法：未执行到的注入点确实不会命中，但**能够在插桩程序中执行的故障组合**，是否对应未修改程序的真实环境状态，还需要接口语义和故障依赖约束。这是迁移到带日志、事务与恢复协议的文件系统时必须补充的论证。

从这两篇论文看，尚没有证据表明它们建立了跨线程事务因果或磁盘持久化状态的通用模型。中断上下文处理解决的是调用栈记录问题，不能自动代替完整并发语义建模。

## 6. 与当前 ext4 仓库的关系

本节依据本次阅读的项目文档讨论设计关系，不将历史实验摘要视为本次重新验证结果。

### 6.1 已有工作与论文方法的互补性

仓库已经描述了：

- ext4/JBD2 的目标 PC、edge 反馈，以及按 syscall 关联的输入、返回值和执行证据。
- 有 errno 来源约束的故障 hook、按种子复现的随机注入及命中隔离。
- 运行时计数、生命周期、稳定快照与离线磁盘检查。
- caller-result 边界注入、较深层原生错误路径与 QEMU 块 I/O 失败的证据区分。

这些内容可分别对接两篇论文的三个部分：

| 层次 | 两篇论文提供的思路 | 当前项目可发展的位置 |
| --- | --- | --- |
| 测试生成 | 输入与故障方案共同搜索 | syscall 序列与 ext4 故障方案关联保存、变异 |
| 搜索反馈 | 调用上下文、实际错误序列 | 将错误上下文和恢复状态特征与 PC/edge 反馈并列 |
| 正确性判定 | 崩溃、内存错误检查器 | 对正常返回但状态损坏的情况，使用独立一致性 oracle |

**更有解释力的研究方向是：上下文敏感的错误路径探索，加上能发现非崩溃语义错误的一致性判定。** 其中反馈决定下一步探索什么，oracle 决定观察到的结果是否违反正确性要求；二者要分别论证。

仓库当前文档描述的 PC/edge、生命周期反馈与随机注入，不足以直接声称已经完整实现 EH-Fuzz 的上下文错误序列模型及双队列调度。是否实现，需要另行检查具体数据结构和运行证据。

### 6.2 优先借鉴的设计

**建议一：把实际故障执行轨迹保存为可重放材料。** 最少关联输入 hash、初始镜像/配置、注入位置、调用上下文、命中次数、errno、执行顺序、实际命中证据。借鉴 possible/covered 的区分，避免将“已 arm”算作“已触发”。输入变化后，原计划也可能不可达，必须重新记录实际执行。

**建议二：优先系统探索单个上下文错误点。** 可先对固定工作负载和初始镜像收集可达错误点，再按允许的失败语义逐个探索。组合故障作为后续阶段，并记录是否新增恢复行为，以控制搜索成本。这是基于论文结果的优先级建议，收益仍需测量。

**建议三：扩展错误点的状态语义，但控制维度。** 一个可研究的扩展是：

```text
FaultCase = <site, call_context, occurrence, errno, state_class>
```

其中 `state_class` 可从事务正常/已 abort、对象生命周期、配置及恢复阶段等有限类别开始。该定义是建议，不是原论文模型，也不是当前仓库已实现声明。应避免直接把原始 inode 号、时间戳等高基数值当作新颖性，造成无意义的种子膨胀。

**建议四：按有效观察边界判断一致性。** 运行中间点、syscall 返回、稳定内存快照、正常卸载、日志恢复后磁盘状态，是不同的判断时机。需要满足相应前提后才能比较；中间态差值、允许的保守恢复和未重放日志不能自动认定为最终一致性缺陷。

**建议五：保留故障真实性的证据层次。** 合法 errno 只说明返回值在接口允许集合内；还需核对该调用上下文是否允许失败、失败前后副作用是否匹配。调用者边界注入验证的是条件错误路径，更深层注入或块层失败可进一步支持环境可实现性。

### 6.3 怎样证明改进有效

建议分别验证两个研究问题，避免同时改变所有因素：

| 实验 | 固定条件 | 改变因素 | 主要观察 |
| --- | --- | --- | --- |
| 错误覆盖反馈实验 | 输入引擎、故障模型、初态、oracle、预算 | PC/edge 反馈与加入错误覆盖的反馈 | 实际上下文/错误序列、新恢复行为、根因级 bug、耗时 |
| 一致性 oracle 实验 | 相同测试语料或可重放执行、故障方案 | 内存检查器与增加一致性检查 | 新增非崩溃缺陷、误报、验证代价 |
| 上下文消融 | 注入位置、errno、工作负载、预算 | 静态位置与上下文区分 | 新可达错误路径、独立根因 |
| 调度消融 | 反馈、种子和 oracle | 随机、固定轮转、停滞切换 | 单位时间收益及不同 seed 的波动 |

至少同时记录代码覆盖、实际错误覆盖、有效语义状态覆盖、根因去重 bug、首次发现时间、执行与重置成本。多随机 seed 的相同墙钟预算有助于评估实用收益，相同执行预算则能补充分析搜索策略本身。

EH-Fuzz 的消融结果已经表明：即使普通分支覆盖下降，也可能发现更多目标 bug。因此，不应仅用 PC 数作为这项工作的最终成功标准。反过来，错误序列数、checker 事件数增加，也不能直接等同于真实 bug 增加。

关于当前仓库既有结果，本次只沿用其文档给出的证据边界，没有重新核验长期实验、修复状态或上游状态。

## 7. 汇报时可直接使用的论述

> FIFUZZ 将故障序列纳入模糊测试输入，并利用源码位置和调用上下文区分错误点，使深层错误处理路径能够被独立触发。EH-Fuzz 在此基础上引入错误覆盖反馈，区分计划故障与实际执行，并分别调度输入变异和故障变异，缓解普通分支覆盖遗漏上下文差异的问题。两篇工作的实验表明，上下文相关的单错误点失败可以揭示大量跨函数错误传播和资源回收缺陷。面向文件系统，可以进一步结合事务、恢复和持久化边界上的一致性 oracle，检测内存检查器难以直接发现的非崩溃语义错误；这一扩展的独立贡献仍需通过受控对照和根因级缺陷证据验证。
